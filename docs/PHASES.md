## Phase B record (2026-10-25)

- **New:** `components/commerce/QuantityStepper.tsx` (shared control; exports `digitsOnly`, `clampQty`), `ProductQuantity.tsx` (product page, min 1, max = in stock capped at 99), `CartLineQuantity.tsx` (cart line: debounce, absolute write through the existing `setCartQuantityAction`, revert and alert on refusal), `CartPending.tsx` (marks line totals and the summary as updating), `lib/modules/pricing/limits.ts` (`MAX_CART_LINES`, `MAX_LINE_QTY`, shared by the client and `pricing/schema.ts`).
- **Behaviour:** "−" stops at 1 (removing stays the separate Remove button); "+" stops at what is in stock or 99; typed values (Latin or Bengali digits) are clamped on Enter or blur; arrow keys step. Buttons are disabled until the page is interactive; without JavaScript the field and an Update button post the same action. The product page still adds through the existing Add to cart form, and the server still refuses more than is in stock counting the cart.
- **Not changed:** server actions, pricing, stock and cart rules, schema, validators, dependencies, CSP, cache headers. The card Quick add stepper is unchanged.
- **Tests:** `tests/unit/quantity-stepper.test.tsx` (7); `tests/e2e-db/commerce/cart.spec.ts` now drives the stepper (+, typed over-stock clamp to 6 with "+" disabled, three rapid "−" giving one consistent quantity that survives a reload).

## Phase C record (2026-10-25)

- **New:** `components/shell/NavigationProgress.tsx`, mounted once in the storefront and admin root layouts (inside `Suspense`, it reads the search params). A 3 px bar at the top edge (`.nav-progress`, `app/globals.css`, colour `--link`) for same-origin link clicks to another page; shown only if the page has not changed within 150 ms; completes when the new route commits (the same moment its `loading.tsx` skeleton appears, so bar and skeleton never show together, and an error or not-found page also completes it); gives up after 10 s if a navigation is abandoned. Ignores modifier keys, new tabs, downloads, other origins and same-page hashes. `role="progressbar"` with a label; reduced motion: no movement.
- **Loading audit:** every storefront and account data route already had a skeleton (account sub-pages share `account/loading.tsx`; static info pages have none and get the bar). Admin: `/admin/notifications` had neither a gate layout nor a skeleton; it now has `gatedLayout` (so the 403/redirect stays real, as in the other sections) and `AdminFormSkeleton`. The admin home keeps no route skeleton on purpose: its setup redirect runs in the page, and a boundary above it would turn that redirect into a streamed 200; its work counts already stream in their own `Suspense`.
- **Not added:** full-screen loaders, artificial delays, a new dependency.
- **Tests:** `tests/unit/navigation-progress.test.ts` (4), `tests/e2e-db/navigation-progress.spec.ts` (3: slow navigation shows one bar that clears, same-page link shows none, reduced motion does not animate).

## Phase D record (2026-10-25)

- **Tests:** `tests/unit/suggest-cache.test.ts` (4); `tests/e2e-db/storefront.spec.ts` new journey: "mini", "min", "mini" asks the server twice, and after an in-app navigation "mini" is asked again.

## Phase F part 2 record (2026-10-25): configurable default language (D31)

- **Audit:** the admin setting already existed (Settings → Store → Default language, `settings.locale.default`, validated `bn | en` by the zod schema and the generated MongoDB validator) but nothing read it. Routing lives in `proxy.ts` (Bengali unprefixed and rewritten to the internal `bn` segment, `/bn/…` → 308, English at `/en/…`); the language switch sets `hb-locale` for a year but nothing used it.
- **Built:** `lib/i18n/entry-locale.ts` (pure decision: explicit cookie first, then the store default, invalid values ignored, entry navigations only) and `lib/i18n/store-default-locale.ts` (reads only `locale.default`, 60 s in-process memo, 800 ms timeout, Bengali on any failure; the admin save clears the memo). `proxy.ts` asks only for an entry navigation without a valid cookie, and answers a 307 with `Cache-Control: private, no-cache, no-store` and `Vary: Cookie, Sec-Fetch-*` before the sign-in redirect, so a guarded page lands on the right language's sign-in. The admin field has a hint explaining the behaviour. No schema, migration or validator change.
- **SSR and client agree:** the language is chosen from the URL before render; `<html lang>`, messages and formatting all come from the URL locale, so there is no flash and no client-side switch.
- **Remaining i18n steps (proposed, not built):**
  - `hreflang` `x-default` still points at `/` (Bengali). That is right while `/` doubles as the entry point, but if the owner makes English the default for good, consider pointing `x-default` at `/en`.
  - Dates and some counts use `Intl` with a fixed `bn-BD`/`en-GB` locale in several components (order dates, admin tables). They ignore the store's numerals setting (`latin` digits on the Bengali storefront) and should move to `lib/format` helpers.
  - The admin is English-only by design; staff email language follows the staff profile.
  - Emails and push messages use the order's or subscription's language, not the store default. That is intended.
  - Each server instance picks up a changed default within 60 s. Clearing it instantly everywhere would need a shared cache tag. Not needed now.
- **Tests:** unit `entry-locale.test.ts` (8, includes the fallback when the database is missing or unreachable); integration `store-default-locale.test.ts` (4, real replica set: saved value, memo, invalid stored value); e2e-db `storefront.spec.ts` D31 test (raw 307 headers and query kept; crawler, same-origin and `/en` not redirected; a fresh browser lands on `/en` with `lang="en"`; the Bengali switch is remembered and wins; an invalid cookie is ignored; back to Bengali stays at `/`).

## Phase F part 3 record (2026-10-25): guest checkout (D28)

- **Audit:** checkout was signed-in only (D13): `/checkout` was a guarded path, `placeOrder` took a `userId` and a saved address, orders were reached only at `/account/orders/<number>` behind sign-in. The device cart (`cart_device` cookie, 32 hex), pricing engine, stock reservations, request keys and the outbox were already independent of the account and are reused unchanged.
- **Checkout without an account:** a signed-out shopper on `/checkout` sees a plain choice first: "Checkout as a guest or create an account for more benefits", the five benefits (saved addresses, order history, rewards while the store runs them, messages with the store, cart and orders on any device), and Sign in / Create account links that come back to checkout. Nothing is pre-selected or hidden; guest checkout is the form below. The delivery area comes first (a no-JS GET form, picked automatically when the store has one area) because it sets the fee; then name, email, BD mobile number, district, area, address, landmark and a note. The form reuses `ActionForm` and the saved-address validation (`cleanAddress`), with an email check added; the server repeats every check.
- **Same order path:** `placeOrder` now takes either a `userId` or a `guest {deviceId, address}`, never both. Pricing, stock, the delivery fee, the expected-total check, the request key (principal `guest:` + a hash of the device id), the cart compare-and-set on the device cart and the transaction are the same code. Coupons limited per customer or to a first order need an account (`coupon_account_required`); guest orders earn no reward points. Rate limits: 5 guest placements per device per minute, 10 claim attempts per account per 10 minutes. Payment stays cash on delivery.
- **Private order link:** each guest order gets a secret link `/order-status/<token>`. The token is an HMAC of the order id under `AUTH_SECRET` (43 characters, 256 bits); only its SHA-256 is stored (`orders.guest.tokenHash`, unique partial index), so a database read does not reveal working links. The page never looks an order up by number, answers 404 for a wrong or unknown link (decided in the segment layout before anything streams), is `private, no-cache, no-store`, `noindex` and carries a `referrer` meta of `no-referrer` (the link is not sent on to other sites). Links work for 180 days, then the page says the link expired and points to the contact page. The confirmation email (when email is configured) and status emails carry the link.
- **Claim, never automatic:** an account whose **verified** email equals the order email sees "Add to my account" on the order page; the claim is a compare-and-set that only succeeds while the order has no owner, and records `guest.claimedAt`. Unverified emails, a different email, or signed-out visitors get an explanation instead. Entering an existing account's email at checkout does nothing to that account. After a claim the link shows only that the order moved to an account.
- **Schema, migration, config:** `orders.userId` is now optional; new optional `orders.guest {tokenHash, expiresAt, claimedAt?}`; validator regenerated (`npm run db:validators`); new index `guest_tokenHash_unique`. No data migration: existing orders all have a `userId`. `AUTH_SECRET` must be at least 32 characters and **stable**: rotating it stops existing guest links from matching (guest checkout refuses to run with a missing or short secret).
- **External setup still needed:** Resend (`RESEND_API_KEY`, a verified sender domain) and `NEXT_PUBLIC_SITE_URL` so the emailed link points at the real site; without email the buyer still gets the link on the confirmation page. Online payments are not built (D15, COD only); a gateway would need an owner decision, keys and webhook setup.
- **Proposed, not built:** a store setting to turn guest checkout off; a "send my order link again" form (would need email and abuse limits); shortening link lifetime after delivery.
- **Tests:** unit `guest-orders.test.ts` (token derivation, hashing, path, claim rules); integration `guest-orders.test.ts` (7: placement through the same transaction, double submit and replay, stale total / empty cart / bad input, coupon rule, lookup only by link and expiry, claim rules and compare-and-set, status emails with the link and no rewards); e2e-db `commerce/checkout.spec.ts` guest journey (benefits text and links, area then form, server-side email refusal, order placed with stock reserved, private status page headers, 404 by order number and by a made-up link, claim with a verified account, claimed link shows nothing); zero-env e2e updated for the new guarded paths.

## Carousel follow-up record (2026-10-25): stacked cards, no pause button (D29 revised)

- **Owner request:** "the carousel should look like a stack" and no pause button, on large and small screens.
- **Before:** a horizontally scrolling row (one card and a peek on phones, two or three cards side by side on wide screens) with a pause/play button.
- **Now:** `components/home/HomeCarousel.tsx` shows one card in front with the next two layered behind it, smaller (92 % and 84 %), dimmed, with a visible edge, offset towards the inline end (14 px phone, 20 px tablet, 26 px desktop). Moving on sends the front card to the back and brings the next one forward (420 ms; no gliding under reduced motion). Card height 176 / 248 / 300 px; on wide screens text slides get larger type and padding, and banner images are requested at the full card width (`sizes`). Cards behind are `inert` and `aria-hidden`, so only the front card is focusable or announced.
- **Controls:** indicators, previous, counter, next; a horizontal swipe (40 px, touch or mouse) moves one card and never follows a link it started on. The pause/play button and its two message keys are removed.
- **Motion rules:** advances every 6 s; holds on mouse hover, keyboard focus inside and a hidden tab; stops for the rest of the visit as soon as the shopper moves it; never under reduced motion. **Accessibility note:** WCAG 2.2.2 asks for a way to pause moving content; without the button the available ways are hover, focus and pressing any control (which stops it). Proposed if a stricter reading is needed: bring back a small pause control.
- **Removed code:** scroll-position measuring (`stops`, `nearest`, ResizeObserver) is no longer needed.
- **Tests:** unit `home-carousel.test.tsx` (7: stack positions, wrap, two slides, timings, markup with inert back cards and no pause button); e2e-db `storefront.spec.ts` carousel test at 375 and 1440 px (stack edge visible, autoplay, focus hold, stop after a press, swipe without following a link, reduced motion). Screenshots checked at 375 and 1440 px.
